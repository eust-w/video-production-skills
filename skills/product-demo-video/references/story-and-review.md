# Product story and review

## Build around a task

A useful default arc is: recognizable problem → ask naturally → inspect evidence → narrow the cause → interact with the result → share or keep watching. Adapt this to the product; it is not a fixed chapter count.

Examples of narration:

- “先看整体情况，再挑最值得关注的部分继续查。”
- “这条线索还不能说明全部原因。我们看看还有什么证据。”
- “需要交给同事时，可以把这段结果带走。”

Useful production questions concern audience, duration, language, or an unknown product behavior. Infer ordinary choices from the request and keep doing independent preparation while an optional answer is pending. The default Xiaoxiao voice is already selected.

## Keep proof separate from the presentation

Test logs can justify readiness without becoming the introduction. In a product demo, show the user's question, visible tool progress when useful, and readable results. Replace verbose recording prompts or API parameter instructions with normal user language when rerecording is possible. Inspect the screen itself, not only the spoken text.

A simulated section can open with “接下来用演示数据介绍……” and retain a small “演示数据” label. Do not narrate fake notifications as real deliveries. If a capability is not connected, preserve that limitation as a short product setup note or omit the failed feature from the main story while keeping the disclosed gap.

## Narration

Use connected sentences and natural pauses. Write what a knowledgeable product guide would say, not a list of function names. Avoid precise speed/quality claims unless measured for the stated case. “It helps organize evidence” is different from “it always finds the root cause.”

Pronunciation is configurable per product; declare the current product’s pronunciation rules. A display/voice mapping changes pronunciation, not meaning. Keep numbers and factual qualifications identical.

Use the original neural boundary timing. A slightly different pause or a removed quote glyph in provider metadata does not justify replacing words or inventing even time slices. If the provider produces incomplete text/audio, regenerate the affected chapter or report the failure.

## Visual review

Review opening, result and exit frames, not only a mid-chapter contact sheet. Look especially for:

- stale conversation content after delete/switch/refresh;
- developer-oriented prose inside reports and export previews;
- crop edges cutting text, graph nodes, or control labels;
- full-screen capture using a different screen size;
- long dead waits, exaggerated slow motion, or long frozen frames;
- captions covering navigation or actions;
- voice, captions, labels, and scene transitions disagreeing;
- a sample/table being presented as complete live inventory.

For a small captured region, excessive enlargement softens text. Prefer a higher-resolution capture or a restrained close-up that keeps enough UI context. A report header, metrics table, and download action can be separate honest close-ups; preserve the demonstration-data label.

After a correction, inspect the changed output, not the previous screenshot. A report should identify the final file/hash and what was actually reviewed; it should not claim every frame was examined from a handful of samples.
